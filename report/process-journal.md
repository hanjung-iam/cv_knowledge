# 作業過程紀錄（Process Journal）

記錄流程中遇到的問題、錯誤、修正方式，以及對 workflow / schema 的修改。格式見 CLAUDE.md 第 13 節。

---

## [2026-11-22] 規劃階段（schema 設計） | 預設 ingest 順序限制了 Wiki 的擴充性

- 現象：CLAUDE.md 初版在 9.2 寫死了 11 份來源的 ingest 順序，並在第 6 節預先登記了這 11 份來源的 cite key。
- 原因：規劃時把「這次作業預計要讀的來源」當成 Wiki 的固定結構，等於在預測使用者之後會加入哪些資料。這和「長期累積、可擴充」的目標互相衝突：加入清單以外的來源時，schema 沒有對應的處理方式。
- 修正（使用者在審閱 schema 時提出）：
  - 9.2 改成「影響評估」：每加入一份新來源，都以當下的 Wiki 為基準，判斷新增、補充、修正與矛盾、關聯、結構、overview 六個面向。
  - 刪除預先登記的 cite key 表，改為 ingest 時才在 source 頁 frontmatter 建立 `cite_key`，schema 只保留命名規則。
  - Ingest 步驟 ① 增加「讀 index 與相關既有頁面」，步驟 ② 的報告必須包含影響評估。
- 是否修改 workflow／schema：是（CLAUDE.md 第 6、9.1、9.2、11 節）。
- 反思：schema 應該描述「怎麼處理任何一份來源」的通用規則，而不是針對特定來源清單的計畫。這個問題在寫入任何 Wiki 內容之前、於 schema 審閱階段就被發現，修改成本最低，這也說明了在規劃階段設置人工審閱的價值。

## [2026-11-22] 工具開發（graph.py） | 無法自動驗證 JavaScript，靠人工審查發現執行期錯誤

- 現象：graph.html 的 JavaScript 中，動畫迴圈第一次執行時就會用到變數 `drag`，但 `drag` 用 `let` 宣告在更後面的位置，瀏覽器會拋出 ReferenceError，整張圖無法顯示。Python 端正常產出檔案，所以「產生成功」不代表「可以使用」。
- 原因：環境中沒有 Node.js，無法對產出的 JS 做語法或執行檢查；這個錯誤是在人工逐段審查程式時發現的。另外也發現每次繪製都重新讀 CSS 變數，頁面多時會變慢。
- 修正：把 `drag` 等互動狀態變數移到最前面宣告；顏色改為讀一次後快取。
- 是否修改 workflow／schema：是。CLAUDE.md 第 11 節新增規則：修改 lint 規則後，要先用含刻意錯誤的假 Wiki 測試。HTML 產物（關聯圖、簡報）的最終檢查一律要在瀏覽器實際開啟，這也是簡報流程 ④「渲染檢查」不能省略的原因。
- 反思：工具的「產出成功」和「產出正確」是兩件事。lint 可以用測試資料自動驗證，HTML 產物目前只能靠人工在瀏覽器確認，這是流程中的一個檢查盲點。
